Case study: Legacy data conversion

How I approach a problem and architect a solution, walked through with a dbt project.

  • Role Analytics engineer, contract
  • Stack dbt, SQL, warehouse, orchestration
  • Timeframe About 6 months

Details are generalized. Company, client, system, and model names have been changed, and figures are shown as ratios or ranges.

1The problem

An organization relied on reporting built on a legacy system that was hard to maintain and being retired. The data had to move to a modern warehouse without breaking the user interface people depended on, and without losing trust in the reports along the way.

2Constraints

  • Messy sources: the legacy data carried years of undocumented logic, with inconsistent keys, mixed formats, and duplicate records.
  • Parity: the new numbers had to match the old ones where they should, and any difference needed an explanation.
  • One-time cutover: the new pipeline was built ahead of time, then the legacy system was turned off, the data loaded, and the new system turned on without disruption. There was no second try.
  • Time and people: about six months, a team of three, and multiple agency stakeholders who needed to sign off.

3Options I considered

Three ways to get from the legacy system to the new one.

Option A: Hand-written SQL

Manually written queries with hardcoded table names and schemas, manual data loads, and stored procedures for orchestration. Easy for many teams to read, but hard to maintain, hard to scale, and slow to build.

Option B: dbt end to end

I demoed dbt to a skeptical team and got the go-ahead to try it. I picked it up quickly and started building models and transformations, with the dbt DAG handling orchestration. Other teams would have had to learn dbt to read and change the load logic.

Chosen

Option C: A combination

dbt for the bronze and silver layers, then stored procedures for the final load, since many teams can read and write them without learning dbt. The tradeoff: no orchestration tool like Airflow, so the DAG was pieced together from the models.

4Architecture

A medallion-style pipeline: dbt for the first two layers and stored procedures for the final load. Two staging layers kept data quality checks separate from type conversions.

The arrows down are the explicit drops: each stage has an excluded counterpart, so a record the conversion can't represent is counted instead of lost.

  • Bronze (included_*): unions each segment's extract files and keeps only what can convert, with data quality tests and the table joins. A matching excluded_* model holds everything else. Tables are named after the legacy files and tables so every record traces back to its source.
  • Silver (stg_included_*): trims, casts, and data type transformations, plus indexes, done once at this boundary so nothing downstream has to.
  • Stored procedures: they load from the silver layer using bulk inserts, so the final step is plain SQL that other teams can read and change.

5Key decisions

  • Full refresh, not incremental: this was a one-time data load, so there was no need for incremental logic.
  • Edge cases: data tests helped flush them out, and I ran test data through the application. The target schema changed constantly because the application was being built at the same time as the pipeline, while the legacy source stayed consistent.
  • Naming for traceability: tables are named for the legacy files and tables, and stored procedures follow bulk_insert_table_name, so anything can be tracked back at a glance.
  • Bulk inserts: the load needed true bulk inserts, not the loop-over-JSON approach you'd typically see with an API.
  • Every drop is explicit: each segment has an included model and an exact-complement excluded model, so a record the conversion can't represent is counted, reconciled, and available to read instead of disappearing between two joins in a loader. Tracing one silent drop this way turned up several thousand records across about a dozen codes.
  • Seeing where the time went: I parsed dbt's run results JSON into a Gantt chart of every thread, which showed where the run was slow. The expected timings in the go-live runbook came from it.
  • Locks under concurrency: dropping foreign keys inside a loader needs an exclusive lock on parent tables that the level's other loaders were already holding, and it failed under parallel load. Dropping and rebuilding them became separate steps before and after each level's fan-out.
  • A go-live runbook: a timed, step-by-step plan with the queries embedded, written so anyone on the team could run cutover without needing me.

Finding the right table in every extract

Each extract named its tables with a different suffix, so models resolve them by prefix. An early version returned an empty list on a miss, which surfaced as a confusing "relation does not exist" error. Now a missing required segment raises an error that lists what the schema actually holds, and an optional segment just warns. The core lookup is below.

Silver: clean once, at the boundary

Fields arrived blank-padded, and every loader trimmed them itself and re-parsed the same dates. Doing both once here removed that repeated work across millions of rows and let a plain index serve the lookups.

Show the code
{{ config(
    alias   = 'included_seg_a',
    schema  = 'silver',
    indexes = [{'columns': ['record_id'], 'type': 'btree'}]
) }}

-- stg_included_seg_a
-- Trim and parse once at the boundary so nothing downstream has to. star() keeps this a
-- passthrough for every other column.
select
    btrim(record_id)                    as record_id,
    public.try_cast_date(begin_date)    as begin_date,
    {{ dbt_utils.star(from = ref('included_seg_a'), except = ['record_id', 'begin_date']) }}
from {{ ref('included_seg_a') }}

A bulk load procedure

Each loader is a stored procedure wrapped in a dbt macro and deployed by a run-start hook, so the whole load is versioned in the project. The migration schema is the schema in the target database where the stored procedures and functions live. The full procedures time every phase, build their rows with CREATE TABLE AS because the planner will parallelize that but never an INSERT ... SELECT, and give ties in any ranking explicit tiebreakers so the same extract gives the same result on every run. The version below keeps that structure and replaces the real queries with a select *.

Show the code
{% macro bulk_insert_entity_address() %}
{% raw %}
-- "migration" is the schema in the target database that holds our procedures and functions
create or replace procedure migration.bulk_insert_entity_address()
    language plpgsql
as $$
DECLARE
    v_count   BIGINT;
    v_started timestamptz := clock_timestamp();
    v_phase   timestamptz;
BEGIN
    RAISE NOTICE '[start] bulk_insert_entity_address';

    -- Build the rows with CREATE TABLE AS: the planner can parallelize it,
    -- but never an INSERT ... SELECT.
    DROP TABLE IF EXISTS migration.entity_address_src;
    v_phase := clock_timestamp();
    CREATE UNLOGGED TABLE migration.entity_address_src AS
    SELECT * FROM silver.stg_included_address;
    CALL migration.log_duration('bulk_insert_entity_address:build_src',
                                clock_timestamp() - v_phase);

    -- Drop the non-constraint indexes so the single-threaded INSERT doesn't pay
    -- index maintenance on every row; they are rebuilt afterward.
    CALL migration.drop_bulk_load_indexes('target.entity_address'::regclass);

    RAISE NOTICE '[step] bulk_insert_entity_address: inserting target.entity_address';
    v_phase := clock_timestamp();
    INSERT INTO target.entity_address
    SELECT * FROM migration.entity_address_src;

    -- Read the row count before any CALL: GET DIAGNOSTICS sees the last statement.
    GET DIAGNOSTICS v_count = ROW_COUNT;
    CALL migration.log_duration('bulk_insert_entity_address:insert_target',
                                clock_timestamp() - v_phase);

    CALL migration.rebuild_bulk_load_indexes('target.entity_address'::regclass);

    CALL migration.log_count('bulk_insert_entity_address', 'inserted', v_count);
    CALL migration.log_duration('bulk_insert_entity_address', clock_timestamp() - v_started);
END $$;
{% endraw %}
{% endmacro %}

Configuration and run hooks

Source schemas come from environment variables, so the same project runs against each load. Tests are set to error and store their failures in a results schema, which is what the triage query reads. Hooks deploy the stored procedures and create the test results tables before any model runs, and log the results at the end. The loads themselves are models: each level is a view whose pre-hook calls one stored procedure, chained with ref() so dbt runs the levels in order.

Show the code
vars:
  primary_source_schema: "{{ env_var('PRIMARY_SOURCE_SCHEMA') }}"
  secondary_source_schema: "{{ env_var('SECONDARY_SOURCE_SCHEMA') }}"

data_tests:
  +severity: error
  +store_failures: true
  +schema: test_results

on-run-start:
  - "{{ deploy_load_procedures() }}"
  - "{{ create_test_results_tables() }}"

on-run-end:
  # The load doesn't run from here. Each level is a model (a view) whose pre_hook calls one
  # stored procedure, chained by ref(), so it has already run by the time this fires.
  - "{{ log_test_results() }}"

Tuning the heavy tables

Models that build tables get session settings through pre-hooks. The cluster's defaults were small enough that sorts spilled hundreds of gigabytes to temp files, so memory went up. Parallelism went the other way: the cluster allowed more workers per query than its shared pool could supply across four dbt threads, and Postgres silently runs a serial plan when the pool is empty, so fewer workers per query meant more real parallelism. One model swung from seconds to minutes between runs on the same code. I treated the memory setting as tuning, not the fix, and noted the query rewrite to measure separately.

Show the code
models:
  my_project:
    silver:
      +materialized: table
      +schema: silver
      # SET LOCAL lasts the transaction dbt wraps each model in. Sized for 4 dbt threads:
      # 4 threads x 4 workers = 16 fits inside the 24-worker pool. The cluster default of
      # 8 per query against a pool of 16 asked for 32, and Postgres silently fell back
      # to serial plans when the pool ran dry.
      +pre_hook:
        - "SET LOCAL work_mem = '512MB'"
        - "SET LOCAL max_parallel_workers = 24"
        - "SET LOCAL max_parallel_workers_per_gather = 4"

6Testing and data quality

  • Data quality tests in the bronze layer, run against the raw data, surfaced edge cases early.
  • Test data was loaded and exercised in the application itself, not just checked in the warehouse.
  • Reconciliation: a custom test confirms that, for every partition, the source row count equals the included plus excluded rows.
  • Triage: every warning and error is classified as new, undocumented, a spike, or known, by comparing it with the full run history and a table of documented exceptions. That put the surprises at the top of the list on go-live day.
  • Query workbooks: additional test suites lived in dbt's analyses folder, each labeled with the level to run it after, and were run alongside the load during go-live.

Source-to-target reconciliation

Show the code
-- tests/assert_staging_counts_match_source.sql
-- source count == included + excluded, for every partition
{{ config(severity = 'warn') }}

{% set domains = partitions() | list | sort %}

with reconciliation as (
    {% for domain in domains %}
    select
        '{{ domain }}' as domain,
        (select count(*) from {{ ref('stg_included_' ~ domain) }}) as included_count,
        (select count(*) from {{ ref('stg_excluded_' ~ domain) }}) as excluded_count,
        {{ source_count_sql(domain) }} as source_count
    {% if not loop.last %}union all{% endif %}
    {% endfor %}
)

select
    domain,
    included_count,
    excluded_count,
    included_count + excluded_count as combined_count,
    source_count,
    source_count - (included_count + excluded_count) as delta
from reconciliation
where source_count <> (included_count + excluded_count)

Go-live triage

This query compared the latest run's failures with the full history.

Show the code
with latest_run as (
    select invocation_id, run_started_at
    from test_results.results
    order by run_started_at desc
    limit 1
),
latest as (
    select f.test_name, f.status, f.failures
    from test_results.results f
    join latest_run lr on f.invocation_id = lr.invocation_id
    where f.status in ('warn', 'error')
),
history as (
    -- worst failure count seen on any earlier run
    select r.test_name, max(r.failures) as max_prior_failures
    from test_results.results r
    join latest_run lr on true
    where r.status in ('warn', 'error')
      and r.run_started_at < lr.run_started_at
    group by r.test_name
)
select
    latest.test_name,
    latest.failures as current_failures,
    history.max_prior_failures,
    case
        when history.test_name is null then 'NEW - never failed before'
        when ke.test_name is null then 'UNDOCUMENTED - has history, not yet triaged'
        when history.max_prior_failures > 0
             and latest.failures > history.max_prior_failures * 1.5
            then 'SPIKE - well above its historical max'
        else 'KNOWN - consistent with history'
    end as classification
from latest
left join history on history.test_name = latest.test_name
left join test_results.known_exceptions ke on ke.test_name = latest.test_name
order by
    case
        when history.test_name is null then 1
        when ke.test_name is null then 2
        when history.max_prior_failures > 0
             and latest.failures > history.max_prior_failures * 1.5 then 3
        else 4
    end,
    latest.failures desc nulls last

For the people using it

The new UI has input constraints and drop-downs, so there is less manual work. It is also easier to access and more secure.

Proving dbt

The project showed that dbt, an open source tool, is valuable for transformation and orchestration in ETL. No one had heard of it or used it before I introduced it.

What I'd do differently

Add an orchestration tool such as Airflow from the start, instead of piecing the DAG together from the dbt models.
